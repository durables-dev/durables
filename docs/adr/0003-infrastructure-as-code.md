# ADR 0003: Infrastructure as code with CDK Terrain

**Status:** accepted, 2026-10-08. **Decided by:** David Dieruf.

## Decision

The entire deployed system is defined in one place: a CDK Terrain project in `infrastructure/`, written in TypeScript, using the Cloudflare Terraform provider. That includes the Cloudflare account resources (D1 database, R2 bucket, DNS records, rate-limiting rules, the Workers Paid settings) **and** the deployable artifacts: the API Worker's code and bindings, and the website's static assets.

Wrangler is used for local development (ADR 0004), as a build step to bundle the API Worker (`wrangler deploy --dry-run`), and to apply D1 migrations in deployment. It deploys no code.

## Why

A single definitive, software-defined description of the system is the point of infrastructure as code. Splitting deployment between a Terraform-based tool for resources and Wrangler for code would leave the system described in two places that can drift. The Cloudflare Terraform provider, from v5.11.0, uploads Worker code and a directory of static assets itself, handling the asset manifest, chunked upload and change detection, so nothing needs to fall outside CDK Terrain. Since 2026-10-09 the Worker is defined with the resources Cloudflare now recommends, `cloudflare_worker`, `cloudflare_worker_version` and `cloudflare_workers_deployment`, rather than `cloudflare_workers_script`: every change is an immutable version, deployed at 100%.

## Consequences

- Deploying means: build `web` and `api`, then `cdktn deploy` from `infrastructure/`. The build outputs are inputs to the infrastructure project.
- The Cloudflare provider must be v5.11.0 or later. The provider version is pinned exactly in `infrastructure/cdktf.json` and its bindings are generated by `cdktn get`.
- CDK Terrain is a pre-1.0 continuation of CDKTF after HashiCorp stopped developing it. Breaking changes between releases are a known risk; its version is pinned and upgraded deliberately.
- Terraform state lives in an R2 bucket used as an S3-compatible backend, with Terraform's native lockfile locking. The bucket is created by hand once, since it cannot be managed by the state it holds. **Decided 2026-10-09.**
- **Secrets are in state, and state is protected.** The provider offers no way to set a Worker secret that keeps it out of state, so the rule is: secrets (sign-in provider client secrets, the session signing key) are sensitive Terraform variables supplied at deploy time, never written into code or any file in the repository, and the state bucket is private, encrypted with a customer-supplied key, and reachable only by its own token. Anyone who can read state can read the secrets; access to that bucket is access to production. **Decided 2026-10-09**, replacing the original "never in state in plain text" rule, which no available mechanism could satisfy.
- D1 migrations are applied in deployment by a Terraform-run step that executes `wrangler d1 migrations apply --remote` before the new Worker version deploys, so local and production migrations go through the same tool and the same bookkeeping. Migrations are additive within a release; a rename or drop waits until no deployed code depends on the old shape. **Decided 2026-10-09.** This is the one Wrangler command that touches production; it deploys no code.
- The Worker resource sets the same `compatibility_date` and compatibility flags as `api/wrangler.toml`, because the API's runtime types are generated from that file (ADR 0004).
- The Worker resource enables Workers Logs (`observability`). The API's logging rules rely on it recording every request.
