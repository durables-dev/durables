# ADR 0008: Detection and checks

**Status:** accepted, 2026-10-08. **Decided by:** David Dieruf.

## Decision

- **Detection is regex-based**, per SDK, for Python, TypeScript and .NET. It finds the SDK, the activity function and its input and output type names, whether it runs synchronously, environment variables read, imports (which also supply "integrates with"), and the signals the behavior checks will later use (heartbeats, non-retryable errors, cancellation handling).
- **Detection is deliberately imperfect.** Someone posts code and it is what it is. What detection cannot tell, it leaves blank. It never asks the publisher to fill the gap and never blocks publishing.
- **Checks run through a pluggable pipeline.** A check is an independent unit that takes the published code and detection results and returns one of _present_, _not present_ or _not applicable_, plus how it was established (_detected_, _declared_, _pattern-matched_, and a reserved _AI-reviewed_). In the MVP the pipeline holds the detection-backed facts the contribute flow's "What we found" card shows and that Configure and the SDK and integration filters read: SDK, activity, input and output, runs as, non-retryable errors, configuration read, dependencies and heartbeats. The behavior checks, with their present, not present or not applicable verdicts and cited lines, and declarations arrive in a later increment as new entries.
- Checks run **at publish**, and their results are stored in the version's document. Nothing re-runs on page views. The contribute flow also runs detection on the pasted file as a preview, so the publisher can see what was found before publishing; that run is informational. The publish-time run is the authoritative one, and the API never accepts detection results from the client.
- **No AI in the MVP.** When Claude-based checks are added, they are new pipeline entries with the _AI-reviewed_ tier, run after publish rather than blocking it, with the submitted code treated strictly as data and never as instructions.

## Why

Regex is cheap, deterministic and good enough for the explicit markers each SDK uses (`@activity.defn`, `[Activity]`, exported functions). Running checks once per immutable version keeps cost proportional to publishing, not traffic. Designing the pipeline as a list of independent checks now means Claude can be added later without redesign, and keeping regex first means Claude is only spent where meaning matters.

## Consequences

- In the MVP a pasted file must contain exactly one activity; files with more are rejected with a clear message. Extracting one activity from a multi-activity file is a later increment, and the extraction approach is **open** until then.
- Detection results are part of the version document (ADR 0005) and therefore immutable with it.
- The Implement snippets (install command, activity, workflow, worker and starter files, run commands) are generated by `api` from the detection results at publish time and stored in the version document too. `web` renders them; it never generates code. The snippet templates are Durables-generated code and follow DUR-2's display rule (line numbers, 4-space indentation); published source is shown exactly as pasted.
- Each check's regex patterns are published as the rubric (a later increment shows them on the activity page), so detection has to be written as named, documented patterns, not ad hoc code.

## Notes
